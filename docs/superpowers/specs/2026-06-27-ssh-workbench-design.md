# SSH 工作台改造设计
日期：2026-06-27

## 背景

当前 SSH 页面已经具备基础能力：可以通过 WebSocket 建立终端连接，支持复制、粘贴、清屏、字体缩放、全屏，以及通过右侧 SFTP 面板完成目录浏览、上传下载、重命名和文件编辑。

它能用，但还不是一个适合高频运维长时间停留的工作台，主要问题有：

1. 页面仍然以“单终端 + 附属文件面板”为中心，不适合多会话并行处理。
2. 终端虽然是主能力，但视觉重心还不够稳，页面气质更像功能页，不像运维主战场。
3. 文件管理、连接状态、快捷操作和终端上下文是并列堆放的，缺少围绕“连续操作”组织的工作流。
4. 当前登录态和连接态更像一次性表单流程，不适合多终端、多标签、断线恢复这类高频场景。
5. 页面不好看并不是单纯的视觉问题，本质上是信息架构、布局权重和状态反馈都没有围绕运维工作方式收拢。

本次改造目标不是把 SSH 页面做成花哨的 IDE 仿品，也不是一次性塞入所有高级功能，而是把它提升为一个更稳定、更高效、更专业的 SSH 运维工作台。

## 目标

面向高频使用 SSH 页的运维工程师，本次改造应满足以下目标：

1. 用户进入页面后，终端应立即成为视觉和操作主角。
2. 用户能够以“标签页 + 按需分屏”的方式组织多个 SSH 会话。
3. 用户在终端、文件、快捷操作之间切换时，不会频繁被弹窗和页面跳转打断。
4. 用户可以清楚感知每个会话的连接状态、认证方式、当前路径、会话时长和异常情况。
5. 页面整体气质从“后台功能页”提升为“专业运维控制台”，但仍保持克制、稳定、信息密度高。

## 非目标

本次改造不包含以下内容：

1. 不做三终端及以上的复杂拼接布局。
2. 不在第一版中实现跨主机并排会话视图。
3. 不实现完整的命令历史检索、会话回放、协同批注等重型能力。
4. 不改变后端 SSH WebSocket 和 SFTP API 的协议形态，第一版以前端重构为主。
5. 不把页面做成营销式视觉展示，不引入与系统整体风格冲突的装饰性设计。

## 最终方向

页面采用“终端偏重的 IDE 式运维工作台”，并明确选择以下主方向：

1. 整体形态采用偏终端的 `B` 方案。
2. 多终端策略采用“标签页 + 按需分屏”。
3. 终端始终是中轴主舞台，文件与辅助信息作为协作侧区存在。
4. 右侧文件区默认常驻，但支持折叠，不再是偶发弹出式工具。

这个方向优先服务于真实运维节奏：

1. 默认场景下保持聚焦，不把页面做得过满。
2. 复杂排障时能快速展开第二终端，而不是先进入另一套页面流程。
3. 文件操作和终端上下文处于同一工作平面，减少来回切换成本。

## 页面结构

### 1. 顶部轻量控制条

页面顶部保留一条低高度控制条，用于承载全局状态和高频控制：

1. 返回入口
2. 主机名与 IP
3. 当前活动会话的连接状态
4. 新建会话
5. 分屏切换
6. 文件侧栏开关
7. 字体缩放
8. 全屏
9. 重连 / 断开

控制条不承担说明性文案，也不做大标题区。它的作用是“保持可控”，不是“解释页面”。

### 2. 左侧窄轨

左侧采用极窄工作轨，而不是传统业务导航栏。推荐宽度 `64px` 到 `84px`，展开态可至 `220px` 左右。

第一版建议包含以下内容：

1. 当前主机入口
2. 最近会话
3. 收藏命令
4. 收藏目录

左轨强调快速进入，不承担复杂详情展示。默认应尽量克制，把横向空间还给终端。

### 3. 中央主工作区

中央主区是页面核心，包含：

1. 会话标签栏
2. 单终端或分屏终端画布
3. 每个窗格的轻量头部
4. 底部状态栏

默认进入时显示单终端。用户可以从标签栏或窗格操作中将当前会话拆分为左右或上下双窗格。

### 4. 右侧协作面板

右侧为常驻协作区，推荐宽度 `300px` 到 `360px`，默认显示文件树。

第一版建议用标签切换以下子区域：

1. 文件
2. 预览 / 编辑
3. 快捷操作
4. 连接信息

它的定位不是“工具箱抽屉”，而是与终端持续协作的第二工作区。

### 5. 底部状态栏

状态栏保持 `28px` 到 `32px` 高度，用于承载低干扰但高价值的持续信息：

1. 当前会话状态
2. 认证方式
3. 终端尺寸
4. 会话时长
5. 当前路径
6. 最近错误或未保存提示

## 多终端模型

### 1. 标签页

标签页是会话组织的第一层。每个标签代表一个独立会话容器，支持：

1. 新建
2. 关闭
3. 重命名
4. 固定
5. 状态提示

标签状态至少包含：

1. 未连接
2. 连接中
3. 已连接
4. 已断开
5. 有未保存文件或未处理异常

### 2. 分屏

分屏是布局呈现层，不是新的导航体系。

第一版只做双分屏：

1. 左右分屏
2. 上下分屏

分屏规则：

1. 由当前标签触发拆分
2. 每个窗格有独立终端实例
3. 每个窗格有独立连接状态
4. 分屏关闭后，可回收为单终端视图

### 3. 状态模型

前端状态建议围绕以下实体组织：

1. `workspace`
2. `sessionTabs[]`
3. `panes[]`
4. `activePaneId`
5. `filePanelState`
6. `connectionState`

核心原则：

1. `tab` 负责会话组织
2. `pane` 负责布局呈现
3. 连接状态从属于具体窗格，而不是整页唯一状态

这样后续扩展双终端、窗格切换和局部断线处理时，状态边界更清晰。

## 关键交互

### 1. 登录与连接

首次进入页面时，显示中心登录卡片，但卡片应服务于“打开一个会话”，而不是“进入一次临时连接”。

连接成功后：

1. 登录卡片退场
2. 当前标签进入已连接状态
3. 状态栏显示连接信息
4. 新建标签时允许复用当前认证或新建独立认证

断线时：

1. 只影响对应标签或窗格
2. 不应导致整个页面回退到初始态
3. 应给出明确重连入口

### 2. 文件协作

文件面板应从“可选工具”升级为“常驻协作区”。

第一版交互原则：

1. 目录浏览和终端并行存在
2. 文件点击优先预览或内嵌编辑
3. 尽量减少打断式弹窗
4. 上传下载要有过程反馈和结果反馈
5. 编辑态需要明确脏状态提示

### 3. 快捷操作

快捷操作不做大而全命令广场，只保留与运维高频场景强相关的内容：

1. 收藏命令
2. 常用目录
3. 快捷动作，如重连、清屏、复制路径、上传、下载

动作入口应尽量图标化，并通过 tooltip 解释，避免形成新的按钮墙。

## 视觉与布局原则

### 1. 终端是视觉中心

页面配色和空间分配必须让终端成为第一视觉焦点：

1. 中央终端区域使用最深层级背景
2. 左右侧面板保持层次，但不要与终端争抢注意力
3. 大块留白让位于真实工作信息

### 2. 克制的控制台气质

页面风格应从“业务后台”收紧为“安静、耐用的控制台”：

1. 弱化卡片感
2. 减少大圆角
3. 降低不必要的高饱和色面积
4. 提高信息密度与扫描效率

### 3. 状态色只服务于状态

颜色只用于关键反馈：

1. 绿色表示已连接或成功
2. 黄色表示警告、重连中、脏状态
3. 红色表示断线、失败、危险操作

不应用大量彩色块装饰界面。

## 第一版实施范围

第一版只解决最有价值的结构性问题，范围如下：

1. `SSHTerminalView` 重构为工作台布局
2. 新增标签页会话模型
3. 支持单终端和双分屏
4. `SSHTerminalToolbar` 改造为轻量控制条
5. `SFTPFilePanel` 改造为常驻右侧协作面板
6. 文件编辑交互从弹窗优先改为侧区优先
7. 增强连接状态与底部状态栏

第一版不做：

1. 三分屏
2. 会话持久恢复
3. 命令历史搜索
4. 跨主机并排
5. 复杂工作区模板

## 组件拆分建议

建议在现有基础上拆出以下组件或状态层：

1. `SSHTerminalWorkbench`
2. `SSHTabBar`
3. `SSHPaneGrid`
4. `SSHPane`
5. `SSHStatusBar`
6. `SSHRightPanel`
7. `SSHSessionState`

其中：

1. `SSHTabBar` 负责会话组织与标签操作
2. `SSHPaneGrid` 负责单终端 / 分屏布局
3. `SSHPane` 负责具体终端实例与局部连接态
4. `SSHRightPanel` 负责文件、预览、快捷操作、连接信息

## 实施顺序

建议分三步完成：

### 第一阶段：骨架重构

1. 重构页面布局
2. 接入左轨、标签栏、主终端区、右侧协作区、状态栏
3. 保持原有单终端能力可用

### 第二阶段：多终端能力

1. 引入标签模型
2. 支持新建会话、关闭会话、切换会话
3. 实现左右 / 上下双分屏
4. 将连接状态收敛到窗格维度

### 第三阶段：协作优化

1. 改造文件交互
2. 增加脏状态提示
3. 增强快捷操作和连接信息展示
4. 优化断线反馈与重连体验

## 验收标准

改造完成后，应满足以下验收标准：

1. 页面首屏一眼可见终端是主舞台。
2. 用户可以通过标签页组织多个 SSH 会话。
3. 用户可以将当前会话一键拆分为左右或上下双终端。
4. 某个会话断线时，不影响其他会话继续工作。
5. 文件浏览、编辑、上传下载与终端可以同屏协作。
6. 页面视觉风格明显比当前更专业、更克制、更像运维工作台。
7. 第一版不引入明显过重的学习成本或过度复杂的布局控制。
