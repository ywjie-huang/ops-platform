# 主机监控页工作台化改造设计

日期：2026-06-27

## 背景

当前主机监控页以标准表格页为主，具备基础的搜索、筛选、排序、分页和自动刷新能力，但整体仍偏“列表展示页”。它能用，但不够像值班场景中的工作台：

1. 首屏对异常的聚焦不够，用户需要先扫表格才能判断当前风险。
2. “上次刷新时间”有存在感，但“数据是否健康、采集是否可信”表达不够。
3. 页面结构比较平均，主次关系不鲜明，异常发现、主机定位、进入处理这三个动作没有被串成连续路径。
4. 现有统计 pills 过于轻量，只能表达数量，不能承担值班入口的作用。

本次改造目标不是把页面做成更复杂的监控大屏，也不是把所有能力都塞进首页，而是把主机监控页提升为一张更成熟的“主机工作台”。

## 目标

围绕运维工程师和 SRE 的日常工作，主机监控页应满足以下目标：

1. 用户进入页面后，10 秒内能判断当前主机监控面的风险状态。
2. 用户能在 30 秒内锁定最值得先处理的主机。
3. 用户能从主列表快速进入详情页或 SSH，不需要在首页分散注意力。
4. 页面在视觉和结构上更成熟，但仍保持克制、可靠、以任务为中心。

## 非目标

本次改造不做以下事情：

1. 不将主机监控页改造成 Grafana 式多图表监控大盘。
2. 不在首页堆叠大块快捷操作入口，如批量执行、巡检、工单等。
3. 不新增复杂的右侧辅助工作栏。
4. 不改变主机详情页、SSH 页、告警页的主体信息架构，只优化首页到这些页面的导流方式。

## 最终方向

主机监控页改造为“监控工作台”，但主舞台明确交给“主机工作列表”。

页面的定位不是激进的风险清单，而是偏“运维台账”的工作面：

1. 默认按风险优先排序，保证异常不会被埋没。
2. 每行保留足够的主机上下文，便于持续筛查、值班浏览和交接。
3. 异常区承担“带你进入重点”的作用，主列表承担“完成判断和进入处理”的作用。

## 页面结构

### 1. 紧凑页头

页头保留如下信息：

1. 页面标题。
2. 最近刷新时间。
3. 自动刷新状态。
4. 手动刷新入口。
5. 数据源健康状态，如 Prometheus 是否正常、采集是否有失败节点。

页头不做大而空的副标题区，也不加入营销式概述文案。它只承担“当前状态”和“刷新控制”。

### 2. 压缩风险摘要

页头下方保留一行压缩的风险摘要，用于帮助用户快速判断当前监控面的整体情况。推荐保留以下四类摘要：

1. 高危主机数。
2. 离线主机数。
3. 指标异常主机数。
4. 近 15 分钟波动主机数。

这些摘要用于判断和导流，不承担完整分析功能。视觉上应比当前统计 pills 更有层级，但不能抢走列表主区域。

### 3. 薄型“优先处理”异常带

在风险摘要下方加入一块较薄的“优先处理”区域，只展示 3 到 5 台最值得先看的主机。

每条异常主机项建议包含：

1. 主机名。
2. 当前最关键的异常原因，如 CPU 97%、磁盘 91%、离线 5 分钟。
3. 持续时长或最近状态变化。
4. 最短处理入口，如 `详情`、`SSH` 或 `告警`。

这块区域只做聚焦，不展开为完整列表，不承载批量操作。

### 4. 主机工作列表

页面主体面积优先给“主机工作列表”。

列表区域应包含：

1. 搜索输入。
2. 状态筛选。
3. 负责人筛选或同等价值的上下文筛选。
4. 排序方式切换。
5. 总量与结果数反馈。
6. 表格主体。
7. 分页。

它是整页的核心工作面，用户大部分时间会停留在这里。

## 列表设计原则

### 1. 气质偏“运维台账”

列表不是只为告警时刻服务，也要支持平稳时段的巡视、筛查和交接。因此它不是极端紧凑的风险清单，而是更完整的主机工作台账。

### 2. 每行保留足够上下文

推荐每行至少保留以下信息：

1. 主机名。
2. IP。
3. 状态。
4. 关键指标，如 CPU、内存、磁盘。
5. 负责人。
6. 采集状态或最近刷新感知。

在现有基础上，可以弱化不常用但占空间的字段，把更多宽度还给主机上下文与状态表达。

### 3. 默认风险优先，但保持可切换

默认排序仍然建议按风险优先，确保异常主机靠前。但用户应能快速切换为：

1. 按主机名。
2. 按 CPU。
3. 按内存。
4. 按磁盘。

排序切换应简洁清楚，不需要设计成复杂多条件面板。

### 4. 行内动作收敛

首页主列表的高频动作只保留：

1. `详情`
2. `SSH`

其他动作不在首页做大面积暴露，避免让监控页变成功能分发中心。

### 5. 状态表达不只靠颜色

离线、告警、高危等状态需要同时依赖：

1. 文字标签。
2. 图标或行级提示。
3. 颜色辅助。

不能只靠红黄绿区分，保证在高密度列表中仍然易读，也兼顾色觉差异用户。

## 应移除或收敛的内容

### 1. 删除独立快捷操作块

浏览器评审中已经确认，独立的“快捷操作”块不符合这个页面的主任务。它会让用户分心，并削弱主列表的地位。

### 2. 删除右侧辅助栏

浏览器评审中已经确认，右侧辅助栏价值不足，且会打散页面注意力。相关信息若确有必要，应以更克制的方式融入页头或列表区上方，而不是保留完整侧栏。

### 3. 控制首页入口数量

首页只为“发现异常”和“进入处理”服务，不为所有周边能力做入口墙。

## 刷新与数据健康表达

当前页面只有“上次刷新时间”和自动刷新开关，改造后应升级为：

1. 最近刷新时间。
2. 当前刷新状态，如自动刷新中或手动模式。
3. 数据采集健康感知，如采集失败节点数、Prometheus 连通状态。

如果采集异常导致数据不可用，页面应明显告诉用户是“数据源异常”，而不是让用户误解为“主机没有数据”。

## 空态与错态

### 空状态

当筛选结果为空时，空态需要区分：

1. 没有任何主机数据。
2. 当前筛选条件没有命中结果。

并提供清晰的恢复动作，如清空筛选。

### 错误状态

错误状态需要分清：

1. 接口加载失败。
2. Prometheus 数据获取异常。
3. 仅部分主机采集失败。

不同错误的提示文案应区分问题来源，避免用户只能看到统一的“加载失败”。

## 视觉与布局原则

1. 延续现有产品的克制风格，不做营销式大卡片。
2. 保持信息密度，但通过层级、留白、字重区分主次。
3. 让主列表成为视觉重心，异常带只是导流，不是第二个主区域。
4. 缩减装饰性模块，把宽度和高度留给真正的工作信息。

## 实施建议

建议分两步实施：

### 第一阶段：页面结构重组

1. 重做页头信息组织。
2. 将当前统计 pills 升级为压缩风险摘要。
3. 新增“优先处理”异常带。
4. 移除右侧辅助栏和独立快捷操作块。
5. 调整主列表为页面主区域。

### 第二阶段：列表与状态细化

1. 重构列表列信息与行布局。
2. 优化状态标签、行层级与异常提示。
3. 优化刷新健康状态表达。
4. 细化空态、错态和部分失败场景。

## 验收标准

改造完成后，应满足以下验收标准：

1. 用户进入页面第一屏即可看出是否存在高危、离线或异常主机。
2. 用户无需扫描完整列表即可发现 3 到 5 台当前最值得先处理的主机。
3. 页面主体视觉重点明确落在主机工作列表。
4. 首页不再出现大块快捷操作区和右侧辅助工作栏。
5. 主列表保留足够主机上下文，符合“偏运维台账”的使用气质。
6. 刷新状态不再只有一个时间点，而是带有数据健康感知。
