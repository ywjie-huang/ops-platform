# AI 会话自动标题设计

## 背景

当前 AI 助手左侧会话列表直接展示 `conversations.title`，但后端创建会话时只使用默认值 `新对话`，后续用户消息、工具调用、最终回答都不会更新标题。因此所有会话在列表里都缺少可辨识度，用户很难回到某一次排障上下文。

目标是让会话列表像 ChatGPT 一样自动出现简短标题，但不能让“你好”“ok”“谢谢”这类低信息量对话污染列表，也不能让标题生成阻塞主聊天流。

## 设计原则

- 主对话优先。标题生成失败、超时或延迟，都不能影响 SSE 回答。
- 只给有信息量的问题命名。寒暄、确认、过短内容继续显示 `新对话`。
- 先快后准。先用规则标题快速改善列表，再异步用 LLM 精修。
- 不反复改标题。自动标题只在默认标题阶段生效，用户后续如果支持手动改名，不能被覆盖。
- 不复用请求 DB session。异步任务必须重新创建数据库会话。

## 推荐方案

采用“规则标题 + 异步 LLM 精修”的两阶段方案。

### 阶段一：同步规则标题

在 `/api/v1/ai/chat` 收到用户消息并写入 `messages` 后，立即判断这条消息是否值得命名。

如果满足条件，后端同步生成一个规则标题并写入 `conversations.title`。这个操作只做字符串处理，不调用 LLM，几乎没有耗时。

示例：

| 用户消息 | 规则标题 |
| --- | --- |
| 今天哪台服务器资源异常？ | 今日服务器资源异常 |
| 最近有什么告警？ | 近期告警查询 |
| 帮我巡检一下系统 | 系统巡检 |
| harbor 为什么指标采集不到 | harbor 指标采集排查 |

如果不满足条件，则保持 `新对话`。

### 阶段二：异步 LLM 精修

当规则标题已生成，并且会话仍处于默认自动标题状态时，启动后台异步任务精修标题。

异步任务使用独立 DB session，读取会话和第一条用户消息，可选读取本轮最终 assistant 回答。生成成功后，如果标题仍是规则标题或 `新对话`，则更新为 LLM 标题。

推荐标题 prompt：

```text
请为下面的运维助手对话生成一个中文会话标题。
要求：
- 6 到 16 个中文字符
- 不要标点
- 不要解释
- 不要使用“新对话”“问题咨询”等空泛标题
- 尽量体现具体对象或操作

用户问题：
{user_message}

助手回答摘要：
{assistant_text_optional}
```

示例：

| 规则标题 | LLM 精修标题 |
| --- | --- |
| 今日服务器资源异常 | 排查今日异常服务器 |
| harbor 指标采集排查 | 排查 harbor 指标采集 |
| 近期告警查询 | 查看近期告警 |

## 触发条件

标题生成只在以下条件都满足时触发：

1. 会话标题为 `新对话`，或带有内部标记的自动规则标题。
2. 当前会话的用户消息数量为 1，或这是首条有意义消息。
3. 用户消息不是寒暄或低信息量内容。
4. 用户消息通过“有意义问题”判定。

### 跳过内容

以下内容不生成标题：

- 空消息或去掉标点后长度小于 6 的消息
- 常见寒暄：`你好`、`hi`、`hello`、`在吗`
- 简短确认：`好的`、`嗯`、`ok`、`可以`、`谢谢`
- 纯身份问题：`你是谁`、`你是什么模型`

这些会话保持 `新对话`，避免列表出现大量无意义标题。

### 生成内容

以下内容应生成标题：

- 包含运维实体或动作：`服务器`、`告警`、`巡检`、`CPU`、`内存`、`磁盘`、`负载`、`容器`、`K8s`、`工单`、`部署`、`Prometheus`
- 明显排障句式：`为什么`、`怎么回事`、`异常`、`失败`、`查一下`、`帮我看`
- 长度足够的业务问题，即使不命中关键词，也可以生成规则标题

## 后端设计

### 新增模块

建议新增：

```text
backend/app/services/ai/titles.py
```

职责：

- `is_title_worthy(message: str) -> bool`
- `generate_rule_title(message: str) -> str | None`
- `maybe_set_rule_title(db, conversation_id, message) -> bool`
- `schedule_title_refinement(conversation_id, user_message, assistant_text=None)`
- `generate_llm_title_task(conversation_id, user_message, assistant_text=None)`

### 数据库写入策略

当前 `Conversation` 只有 `title` 字段，没有标题来源字段。第一版不新增表字段，减少迁移复杂度。

为了避免覆盖未来手动标题，第一版只在 `title == "新对话"` 时写规则标题。LLM 精修只在标题仍等于规则标题时覆盖。

如果后续要支持用户手动重命名，建议再增加：

```text
title_source: manual | rule | llm
```

但本次设计不强制引入该字段。

### 异步任务策略

使用 `asyncio.create_task()` 即可，不引入 Celery 或外部队列。

异步任务内必须重新创建 DB session：

```python
db = SessionLocal()
try:
    ...
finally:
    db.close()
```

任务失败只记录日志，不向用户返回错误。

### LLM 调用策略

标题生成应该复用当前系统配置里的 LLM profile，但参数更保守：

- `temperature`: 0.2
- `max_tokens`: 32 或 64
- 不传 tools
- 使用简单非工具对话

如果当前模型配置不可用，则跳过 LLM 精修，保留规则标题。

## API 与 SSE 设计

第一版不新增 API，也不新增 SSE 事件。原因是前端已经会在回答结束后 `loadConversations()`。

为提高异步标题命中率，前端在收到 `done` 后：

1. 立即刷新会话列表。
2. 延迟 1.5 秒再刷新一次。

这样不需要 WebSocket 或轮询，也能覆盖“标题任务稍晚完成”的情况。

后续如果希望标题实时更新，可以新增 SSE 事件：

```json
{"type": "conversation_title", "conversation_id": 1, "title": "排查今日异常服务器"}
```

但第一版不做，避免扩大 SSE 协议面。

## 前端设计

前端现有左侧列表已经展示 `conv.title`，因此主要改动很小：

- 回答结束后继续调用 `loadConversations()`。
- 增加一个延迟刷新：`setTimeout(loadConversations, 1500)`。
- 如果当前会话仍显示 `新对话`，二次刷新后自动替换为新标题。

不需要单独的 loading 状态。标题是辅助信息，不应占用用户注意力。

## 失败与兜底

- 规则判定为无意义：保持 `新对话`。
- 规则标题生成成功，LLM 精修失败：保留规则标题。
- LLM 返回空、过长、包含标点或解释：清洗后不合格则丢弃。
- 异步任务执行时会话被删除：直接退出。
- 用户后续如果手动改名：标题任务不得覆盖。

## 测试计划

### 后端单元测试

新增 `backend/tests/test_ai_conversation_titles.py`：

- `你好`、`ok`、`谢谢` 不生成标题。
- `今天哪台服务器资源异常？` 生成规则标题。
- `harbor 为什么指标采集不到` 生成包含 `harbor` 的标题。
- 标题长度被限制在合理范围。
- `title != 新对话` 时不覆盖。
- 异步任务使用新的 DB session，不复用请求 session。

### API 测试

扩展 AI chat 测试：

- 新会话首条有意义消息后，conversation title 不再是 `新对话`。
- 寒暄消息后仍为 `新对话`。
- 回答完成后不因标题任务失败导致 SSE error。

### 前端测试

扩展 AI View 源码或纯函数测试：

- `done` 后会触发一次立即刷新。
- `done` 后会触发一次延迟刷新。
- 不影响当前消息流显示。

## 不做项

- 不引入 Celery、Redis 队列或定时任务系统。
- 不为每条消息都重新生成标题。
- 不在主 SSE 回答前等待 LLM 标题。
- 不为寒暄和极短信号生成标题。
- 第一版不新增手动重命名入口。
- 第一版不新增标题生成开关；后续如果用户需要，可放到模型配置页。

## 推荐落地顺序

1. 新增标题规则模块和后端单元测试。
2. 在 `/ai/chat` 首条用户消息后写入规则标题。
3. 加入异步 LLM 精修任务，失败只记录日志。
4. 前端 `done` 后增加延迟刷新。
5. 补充 API 与前端测试。

## 决策结论

采用“两阶段标题生成”：

- 第一条有意义用户消息后，同步写入规则标题。
- 主回答流程继续，不等待标题。
- 回答结束后异步调用 LLM 精修标题。
- 前端在回答完成后立即刷新，并延迟刷新一次。

这个方案在体验、稳定性和实现复杂度之间比较均衡：用户能很快看到有意义标题，LLM 标题失败不会影响聊天，低信息量对话不会污染列表。
