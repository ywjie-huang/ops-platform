# 主机详情页优化设计

日期：2026-06-29

## 背景

当前 `HostDetailView` 已经具备基础详情能力：返回、Prometheus 状态、SSH 入口、CPU/内存/磁盘/负载概览，以及系统、CPU、内存、磁盘、网络等信息面板。它能展示数据，但更像“指标详情集合”，还没有充分承担主机监控点击详情后的核心任务：快速判断风险、定位异常原因、进入处理动作。

主机列表页已经在向“风险优先”的工作台方向演进，详情页也应该接上同一条动线。用户从列表点击某台主机时，通常不是为了慢慢浏览档案，而是为了回答三个问题：

1. 这台主机现在严不严重？
2. 主要异常在哪里，是否还在恶化？
3. 我下一步应该做什么？

本次规划确认采用 **A + C 混合方向**：以“排障指挥台”为主，在详情页中加入“趋势和事件时间线”的诊断能力。

## 目标

1. 用户进入详情页后，首屏 5 秒内能判断主机健康状态和最高优先级问题。
2. 用户不用在多个面板之间跳读，就能看到异常指标、趋势方向、持续时间和建议动作。
3. 用户能从详情页直接进入 SSH、复制 IP、查看关联告警、容器、部署或巡检记录。
4. 页面保持产品工具感：高信息密度、克制视觉、清晰层级，不做大屏化或营销化设计。
5. 在后端历史指标或事件数据尚不完整时，也能先完成首屏结构优化，并为后续增强留出位置。

## 非目标

1. 不把主机详情页改造成完整 Grafana 面板。
2. 不在详情页堆放所有运维功能入口。
3. 不引入新的图表库作为首期必要条件，优先复用当前轻量 SVG/DOM 图形风格。
4. 不改变 SSH 终端、告警、容器、部署、巡检等模块的主体业务流程。
5. 不在首期强依赖 AI 诊断结论；如果以后接入 AI，应作为辅助说明而不是主判断来源。

## 最终方向

详情页定位为 **单主机排障指挥台**。

页面不是平均铺开所有字段，而是按排障优先级组织：

1. 顶部回答“这是谁、是否在线、数据是否可信、能做什么”。
2. 首屏核心区回答“当前判断、异常指标、建议动作”。
3. 第二层回答“异常是否持续、是否和事件相关”。
4. 下方再承载系统档案、网络、磁盘 IO 等稳态详情。

简化成一句话：**A 的动作优先 + C 的诊断上下文**。

## 页面结构

### 1. 顶部身份栏

顶部区域应保持紧凑，替代当前较普通的“主机详情 + 状态 + SSH”组合。

建议展示：

1. 返回按钮。
2. 主机名。
3. 风险状态标签，例如 `正常`、`关注`、`高风险`、`离线`。
4. Prometheus 或采集状态。
5. IP、业务/环境、负责人、最近刷新时间。
6. 高频动作：`刷新`、`复制 IP`、`SSH 连接`。

设计要点：

1. 主机名和风险状态必须是一眼可见的第一视觉层级。
2. 采集状态需要和主机状态区分，避免用户把“无数据”误解为“主机正常”。
3. SSH 是主要动作，复制 IP 和刷新是辅助动作。

### 2. 当前判断区

首屏核心区左侧放“当前判断”，负责把多项指标压缩成运维可读的结论。

建议内容：

1. 当前健康结论，例如“CPU 持续高位，Load 继续上升，建议先确认进程和近期发布”。
2. 处理优先级，例如 `需处理`、`观察中`、`正常`。
3. 关键指标卡：CPU、内存、磁盘、Load。
4. 指标变化方向，例如 `+12%`、`平稳`、`超过基线`。

设计要点：

1. 指标卡不使用大圆环作为主视觉，改为更紧凑的数值 + 横向进度条。
2. 异常指标通过文字、颜色、边框和排序共同表达，不能只靠颜色。
3. Load 的表达应结合 CPU 核心数，而不是简单映射成百分比。

### 3. 建议动作区

首屏右侧放建议动作，承接“发现问题后下一步做什么”。

首期建议保留 3 个动作：

1. SSH 查看高 CPU 进程。
2. 核对最近发布或变更。
3. 同步负责人，例如复制摘要或创建工单入口。

设计要点：

1. 动作按优先级排列，最多 3 条，避免变成入口墙。
2. 每条动作应附带一句上下文，例如“10:55 有发布事件”。
3. 若没有相关数据，降级为通用动作，例如“进入 SSH 排查”。

### 4. 指标趋势区

第二层左侧放趋势，吸收方案 C 的诊断能力。

建议展示：

1. CPU 趋势。
2. Load 趋势。
3. 内存趋势。
4. 网络趋势。

首期可以使用轻量趋势图或迷你折线，不必做完整交互图表。趋势图的目标不是替代专业监控图，而是帮助用户判断：

1. 是瞬时尖峰还是持续升高。
2. 异常从什么时候开始。
3. 多项指标是否同步变化。

如果后端暂时没有历史序列，首期可以保留趋势区结构，但显示“暂无历史趋势”，并优先实现当前判断区。

### 5. 事件时间线

第二层右侧放时间线，用于连接指标异常和运维事件。

建议事件来源：

1. Alertmanager 告警。
2. 应用部署记录。
3. 巡检记录。
4. 容器状态变化。
5. 手工操作记录，如果系统已有审计日志能力。

时间线展示规则：

1. 默认展示最近 24 小时。
2. 最多展示 4 到 6 条，避免压垮详情页。
3. 每条事件包含时间、类型和一句摘要。
4. 可点击跳转到对应模块详情。

首期如果事件来源不足，可以先接入告警和部署记录；其他来源后续补齐。

### 6. 关联跳转

时间线下方或右侧底部放“可跳转关联”，作为轻量导航，而不是大块快捷操作区。

建议入口：

1. 相关告警。
2. 容器列表。
3. 最近部署。
4. 巡检记录。

设计要点：

1. 入口展示数量或最近状态，例如“相关告警 2 条”。
2. 不做醒目的彩色大按钮，避免抢首屏排障动作的注意力。
3. 没有数据时显示灰色弱化状态，而不是隐藏导致布局跳动。

### 7. 稳态详情区

系统信息、网络、磁盘 IO 等放在趋势区下方。

建议拆成三组：

1. 系统信息：规格、系统、运行时间、进程数、负责人。
2. 网络：入站、出站、TCP 连接。
3. 磁盘 IO：容量、读速率、写速率。

当前 `el-descriptions border` 信息密度较高但视觉重量偏重。后续实现时可改为更轻的键值网格，减少表格边框噪音。

## 数据模型建议

当前 `HostDetail` 已有：

1. 主机身份：`hostname`、`ip`、`spec`、`os_info`、`owner`、`status`。
2. 采集状态：`prometheus_ok`。
3. 当前指标：CPU、内存、磁盘、网络、Load、TCP、进程数、运行时间。

为完整支持 A + C 方向，建议后续扩展：

1. `risk`: 主机风险等级、主异常原因、建议摘要。
2. `metric_trends`: CPU、Load、内存、网络的短窗口历史序列。
3. `events`: 最近告警、部署、巡检、容器变化等事件。
4. `relations`: 相关告警数、容器数、最近部署数、巡检记录数。
5. `recommendations`: 建议动作列表，每项包含动作类型、文案、跳转目标和上下文。

如果希望控制后端改动，首期可以不新增完整字段，而在前端根据现有字段派生风险等级和建议动作。

## 交互规则

### 刷新

1. 保留手动刷新。
2. 显示最近刷新时间。
3. 如果未来详情页开启自动刷新，需要使用 `onActivated` / `onDeactivated` 管理定时器，保持和项目 keep-alive 约定一致。

### SSH

1. SSH 连接作为主按钮保留在顶部。
2. 建议动作区中的 SSH 动作应跳转到同一目标，不创建第二套入口逻辑。

### 错误与无数据

1. 接口加载失败：显示可重试错误态。
2. Prometheus 不可用：保留主机档案，指标区显示采集异常说明。
3. 部分指标缺失：只弱化对应指标，不让整个详情页失败。
4. 历史趋势缺失：趋势区显示占位说明，不影响当前指标和动作。

### 响应式

桌面端：

1. 首屏使用两列布局：左侧当前判断，右侧建议动作。
2. 第二层使用左侧趋势、右侧时间线和关联跳转。

移动端：

1. 顶部动作换行。
2. 当前判断、建议动作、趋势、时间线纵向排列。
3. 指标卡从四列降为两列或一列。
4. 所有按钮和跳转入口保持可触达，不依赖 hover。

## 视觉原则

1. 使用现有设计 token：`--primary-color`、`--success-color`、`--warning-color`、`--danger-color`、`--surface-color`、`--border-color` 等。
2. 页面保持浅色、克制、工具化，不做大面积渐变或装饰背景。
3. 卡片圆角不超过当前系统风格，优先使用 `var(--border-radius)`。
4. 风险状态同时使用文案、色彩、排序和边框语义。
5. 趋势图只承担方向判断，不追求完整图表系统。
6. 动效只用于 hover、focus、加载骨架，不做页面入场动画。

## 分期实施建议

### 第一阶段：前端结构优化

目标是在现有 `getHostDetail` 数据上完成页面重组。

内容：

1. 重构顶部身份栏。
2. 把圆形概览改为紧凑关键指标卡。
3. 增加当前判断文案，前端根据现有指标派生。
4. 增加建议动作区，首期使用静态规则生成。
5. 把现有详情信息下沉为稳态详情区。
6. 优化 loading、error、Prometheus 异常状态。

这一阶段不要求后端新增接口。

### 第二阶段：趋势和时间线

目标是补齐 C 方案的诊断上下文。

内容：

1. 后端增加短窗口历史指标，或新增趋势接口。
2. 详情页接入 CPU、Load、内存、网络趋势。
3. 后端聚合最近告警、部署、巡检等事件。
4. 前端展示最近 24 小时时间线。
5. 关联跳转入口显示真实数量和状态。

### 第三阶段：动作闭环

目标是让建议动作从“提示”变成“可执行流程”。

内容：

1. 支持复制排障摘要。
2. 支持从详情页创建工单并带入主机和异常信息。
3. 支持跳转容器列表并按当前主机过滤。
4. 支持跳转告警页并按当前主机关联。

## 验收标准

1. 从主机列表点击详情后，首屏能看到主机名、IP、风险状态、采集状态和 SSH 入口。
2. 当前判断区能明确指出最高优先级异常，不需要用户逐个读取所有面板。
3. CPU、内存、磁盘、Load 的状态表达比当前圆环更紧凑，且不会只依赖颜色。
4. 页面包含建议动作区，且 SSH 是最主要处理动作。
5. 趋势和时间线在视觉上是诊断辅助层，不抢当前判断区的主次关系。
6. Prometheus 异常、接口失败、部分指标缺失都有明确状态。
7. 移动端不出现文本溢出、按钮挤压或信息重叠。
8. 首期实现不破坏 keep-alive 下的 `onActivated` 数据获取模式。

## 后续评审问题

1. Load 的风险阈值是否按 `load1 / cpu_cores` 判定，还是沿用当前简单映射？
2. 事件时间线首期优先接入告警，还是告警 + 部署？
3. 是否需要在详情页支持自动刷新，刷新间隔是否和列表页保持 15 秒一致？
4. “复制排障摘要”是否进入首期，还是放到第三阶段？
